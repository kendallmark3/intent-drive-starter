Architecture / Intent-Driven Engineering / Rev. 02

Start with the smallest useful intent. Build it, look at it, then decide: continue or stop.

Most AI-assisted workflows start from a prompt and hope the model inferred the right thing. This starter asks for two things up front: the outcome, and how success will be judged. It builds the smallest change worth looking at, and what the human sees in the running result becomes the next small change instead of a bigger specification.

The operating model

Equation
Repository State + Next Intent = Next Repository State

The repository is the source of current-state truth. The human does not restate what the code, tests, and context already say.

Working loop
Intent → Build → Observe → Learn → Refine → Continue or Stop

The human owns the outcome, the boundaries, and the decision. The AI owns the reasoning, the plan, and the implementation.

Shared supply — read by the loop, not part of it

Repository state
code · tests · context/

What already exists. context/ holds only what the code cannot show: architecture, business rules, glossary, integrations, security.

templates/
feature · delta · bug · ADR

Fixed shapes for an intent, the delta that follows an observation, a defect, and an architecture decision.

The loop

  1. N01 Intent

    Project Intent

    intent/project-intent.md

    Purpose, business outcomes, and constraints for the whole system. Written once, revisited whenever the system's reason for existing changes.

  2. N02 Intent

    Current Feature

    intent/current-feature.md

    Outcome and Success / Evidence are enough to start. Inputs, outputs, and boundaries are added only when they are real. Deltas from later cycles are appended here; the original intent is never rewritten.

  3. N03 Gate

    Pre-Implement Hook

    hooks/pre-implement.sh · hooks/hooks.json

    Blocks code edits until N02 states an outcome and how success will be evidenced. It checks that the intent is sufficient, not that it is a complete specification. Markdown is never blocked.

  4. N04 Build

    Smallest Useful Delta

    skills/feature-planner · agents/planner.md · agents/developer.md

    Reads repository state and the intent, then builds the smallest change worth looking at. The approach belongs to the AI unless the intent sets a boundary.

    reads repository state
  5. N05 Verify

    Post-Implement Hook + QA Agent

    hooks/post-implement.md · agents/qa.md

    Runs tests, updates docs, and checks the result against the evidence N02 asked for, before it is handed to the human.

  6. N06 Observe

    Human Observation

    the running result

    The human looks at what was actually built and says what they think in ordinary words: keep this, change that, this is too busy, don't touch the backend.

  7. N07 Decide

    Continue or Stop

    skills/progressive-intent · templates/delta-template.md

    Every cycle ends here. Continue: the observation becomes a delta (Observation, Keep, Change, New Boundary, Evidence) and the loop runs again. Stop: the work moves on to review.

    ↑ Continue — append a delta to N02 and return to N03
  8. N08 Review

    Pre-PR Hook + Reviewer Agent

    hooks/pre-pr.md · agents/reviewer.md

    On Stop. Verifies checks are green and reviews the change against the intent and its deltas, not just the diff.

    ↑ checked against N02 — Current Feature
  9. N09 Ship

    CI Pipeline

    .github/workflows/ci.yml

    The last automated gate before merge.

Why teams start here

Start small, not fully specified

An outcome and a way to judge it are enough to begin. Nobody has to predict the requirements, the architecture, and every acceptance criterion before seeing anything.

The human judges results, not plans

Feedback is given on something running, in plain language. The human never has to prescribe the implementation to get the change they want.

Deltas, not rewrites

Each iteration records only what changed and what must stay. The history of the feature reads as a short chain of observations instead of a specification edited in place.

One deterministic gate before code

The pre-implement hook enforces a rule a script can check. It does not dictate how the AI reasons or plans.

Every cycle ends in a decision

Continue or stop is asked explicitly, so work ends when another change would no longer produce value.

Discipline is kept, applied when justified

Architecture, testing, security, documentation, QA, review, and CI all remain. They are brought in when the problem and the evidence call for them, not guessed at in the first intent.
